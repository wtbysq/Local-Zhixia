1结论与环境事实核对

桌面化最容易踩的坑，是选了一个本机根本装不上的壳。所以先测，再定。

用 pywebview 当壳，把现有 HTTP 服务塞进同一个进程，窗口直接渲染现有的 web/。

它不是另一套技术栈，而是一个「把系统 WebView2 包成 Python 窗口」的薄库：约 1 MB 代码，没有 Node、没有 Rust、没有构建步骤。核心的 server/ 仍然零第三方依赖，随时可以退回浏览器模式。

核对项实测结果对方案的影响
WebView2 运行时已安装，版本 156.0.4314.42（Win11 预装）窗口能有 Chromium 内核，前端无需降级
Edge 浏览器156.0.4314.42可作为 WebView2 缺失时的回退方案
pywebview6.2.1，纯 Python 轮子可取壳本身没有编译依赖
pythonnet（Windows 后端）3.2.1，含 cp311.cp312.cp313 轮子Python 3.13 可以直接用，不需要降版本
PyInstaller6.22.3（win_amd64）可打包成 exe
PyPI 可达性pypi.org 直连不稳定；阿里云镜像可用；清华源缺 pywebview安装与未来重装都走阿里云源
引擎运行时runtime/llama 1.0 GB，DLL 与 exe 同目录决定打包只能 onedir，不能 onefile
诚实交代一个代价

现在的程序是零第三方依赖——只用 Python 标准库，连 venv 都不需要。桌面化必然打破这一条：至少要多一个 pywebview（连同 pythonnet 约 10 MB），构建期还要 PyInstaller。

所以方案里保留双入口：桌面壳坏了，python server/main.py 仍然能跑，浏览器照样用。核心的 server/ 目录不引入任何第三方包，这条底线不破。

2四条路线对比与取舍

判断标准不是「谁更流行」，而是「在我们已有的东西上，谁需要重写得更少」。

路线它是什么能复用什么要付什么代价结论
pywebview
推荐		 Python 薄壳，调用系统 WebView2 开窗口 后端 100%、前端 95%；新增约 150 行启动代码 1 个运行时依赖；打包需 PyInstaller；pythonnet 偶有版本兼容问题 ✅ 改得最少
Tauri Rust 壳 + 系统 WebView2，前端仍是网页 前端可复用；后端要作为 sidecar 打包 装 Rust + Node 工具链；Python 后端要额外打一次包再被 Rust 调用，变成两层打包 △ 体积最小，但工程复杂度翻倍
Electron 自带 Chromium 的桌面运行时 前端可复用；后端仍需 sidecar +150 MB 起；Node 工具链；同样两层打包 ❌ 与「依赖少」冲突
原生 GUI
PySide6 / tkinter		 用控件库重画界面 只能复用后端 现有 1000+ 行前端全部作废，Markdown 渲染、流式追加、代码高亮都要重写 ❌ 投入产出比最差
为什么不选 Tauri（它确实更"现代"）

Tauri 的优秀建立在「前端是唯一产物」这个前提上。我们的重头戏是 Python 侧：模型适配器、进程托管、SQLite、上下文引擎。用 Tauri 就得把 Python 打成 sidecar，再被 Rust 拉起来——原本一个进程能解决的事，变成两个打包产物、两套日志、两处崩溃。

等哪天要发布给别人、需要自动更新和安装包时，再考虑 Tauri 也不迟。那时候换壳只影响 app.py 一个文件。

3目标架构：入口、承载、运行方式

3.1 进程结构

桌面主进程
app.py → 启动 → HTTP 线程
127.0.0.1:临时端口 → 拉起 → llama-server 子进程
127.0.0.1:8090
WebView2 窗口
加载 web/ 静态页 ⇄ fetch / SSE ⇄ SQLite
data/app.db ⇄ 流式读取 ⇄ GGUF
models/

窗口与 HTTP 服务在同一个进程里，只有引擎是子进程。关窗口即回收全部资源。

3.2 三个必须明确的定义

维度定义
入口方式双击 本地模型工作台.exe。启动顺序：单实例检查 → 准备数据目录 → 后台线程起 HTTP（端口交给系统分配，不再固定 8787）→ 轮询 /api/health 就绪 → 开窗加载 http://127.0.0.1:{实际端口}。任一步失败弹原生对话框说明原因，而不是白屏。
界面承载系统 WebView2（Chromium 内核）渲染现有的 web/。不做前端重写，只改 3 处桌面适配：外链交给系统浏览器、导出改用原生保存对话框、可选的无边框标题栏拖拽。
本地运行方式全部在本机：HTTP 只绑 127.0.0.1（回环，不触发防火墙提示）；模型与数据库都在本地磁盘；无遥测、无联网检查。窗口关闭 → 停 HTTP → 停引擎 → 进程退出，不残留。

3.3 端口为什么要改成动态分配

网页版固定用 8787，是因为你要在浏览器地址栏里记住它。桌面版没有这个需求，反而有三个坏处：一是和网页版同时开会抢端口；二是端口被别的程序占用时启动失败；三是固定端口更容易被本机其它程序探测。

改法很小：start_in_thread(port=0) 让系统分配，窗口用返回的实际端口。网页版仍然读 config.json 的 port，行为不变。

打包形态的硬约束

引擎运行时是 1.0 GB（llama-server.exe + 20 多个 DLL + CUDA 库）。这直接排除 onefile：单文件模式每次启动都要把这 1 GB 解压到临时目录，冷启动会从 3 秒变成几十秒，还会在 %TEMP% 留下副本。

所以发布形态是 onedir 文件夹：一个目录、一个 exe、旁边是 runtime/ web/ models/。压缩后约 400 MB（引擎 DLL 压缩率高），解压即用，不需要安装程序。

6风险与对策

按「会不会挡住交付」排序，不是按发生概率。

风险表现对策
WebView2 缺失
老 Win10 或精简系统		窗口白屏或创建失败启动时读注册表/目录探测；缺失则弹框给出安装指引，并自动回退到系统浏览器打开，功能不中断
pythonnet 运行时异常import clr 失败，窗口起不来D1 第一件事就验证；失败则退回「Edge --app 模式」（无边框浏览器窗口，观感接近但仍算独立窗口）
打包后路径错乱启动即报找不到模型 / 找不到 web统一 BASE_DIR = exe 目录；禁止使用 sys._MEIPASS 解析 runtime/、models/；D3 用干净账户验证
1 GB 运行时包体大、传输慢onedir + zip；不做 onefile；引擎目录单独一层，升级引擎不必重打整个包
杀软误报
PyInstaller 常见		exe 被拦或删提供两条路：正常 exe；以及「便携脚本版」（python + 源码 + 快捷方式），后者不触发误报
多实例抢资源两个窗口各起一个引擎，8 GB 显存直接爆启动前用命名互斥量/锁文件判定，已有实例则唤起原窗口并退出
关窗后引擎残留显存不释放，下次启动 8090 被占on_closing 显式 stop_engine()；启动时读 PID 文件清理上次的孤儿进程
数据目录不可写装在 Program Files 时无法写库数据默认放 exe 旁（便携）；若检测到不可写，自动迁到 %LOCALAPPDATA% 并在界面提示
导出/外链失效点导出没反应，点链接把应用变成浏览器用 pywebview 的 JS API 接管：导出弹原生保存框，外链交 os.startfile
最需要提前接受的一条

桌面化之后，「改一行代码就能用」的便利会下降：调试从「刷新浏览器」变成「重启窗口」，改前端后还要重新打包才生效。

缓解办法是双入口长期保留：开发时用 python server/main.py + 浏览器（改完刷新即见），交付时才用 exe。不要把浏览器模式当成过渡产物删掉。
