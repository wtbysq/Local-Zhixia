一句话判断

如果你的目标只是「在本地跟模型聊天」，那么装一个 Open WebUI 或直接用 LM Studio 自带对话窗口，半小时就够，不必自建。自建的真实价值在于三件事：参数可被精确钳制（防止一调 n_ctx 就把 8GB 显存打爆）、上下文预算透明可见（知道模型为什么"忘记"了前文）、以及能作为你自己的工具链底座继续长（接 RAG、接工具调用、接批处理脚本）。如果这三件事你都不需要，选现成方案更划算。

1整体架构与职责划分

核心原则：推理归推理，业务归业务，渲染归渲染。三者用一条 HTTP 边界隔开，任何一层都可以单独替换而不影响其他两层。

1.1 进程拓扑与数据流

数据流一句话：用户输入 → 后端拼上下文 → 推理服务流式吐 token → 后端封成 SSE 帧 → 前端逐字上屏 → 落盘。整条链路上只有三个 TCP 端口，全部绑定 127.0.0.1，没有一处需要出网。

1.2 四层职责边界

划清"谁不该做什么"比划清"谁做什么"更重要——绝大多数本地 AI 项目的返工，都源于把职责放错了层。

层组件职责明确不该做的事
L1 推理层 LM Studio（llama.cpp 内核） 权重加载与 GPU 卸载、分词、采样、KV cache 管理、并发 slot 调度 不存任何业务数据；不做会话管理；不实现上下文裁剪策略
L2 接入层 标准库后端（http.server） 协议转换（OpenAI ↔ 前端自定义事件）、参数合法性钳制、上下文预算与裁剪、SSE 帧封装、断流兜底、日志与指标 不自己实现推理；不精确复算 token（以服务端返回的 usage 为准，本地只做粗略预估兜底）；不做前端渲染逻辑
L3 展示层 原生 HTML/CSS/JS 增量 DOM 更新、Markdown 与代码渲染、交互状态、快捷键 不直连推理服务（否则必须开 CORS 并暴露推理端口）；不存权威数据（本地缓存仅作兜底）
L4 存储层 SQLite 单文件 会话、消息、参数预设、使用统计 不存模型权重（模型由推理层管）；不做全文检索先用 LIKE，够用了再上 FTS5
为什么不能省掉后端

纯前端直连推理服务看起来很诱人（少一个进程），但会立刻撞上四堵墙：① 必须给推理服务开 CORS，等于把 1234 端口向本机所有网页敞开；② 上下文裁剪需要 token 计数与预算判断，放前端做则每个标签页各算一套，结果不一致；③ 断流后无法把"已经生成的半截回答"可靠落盘；④ 参数钳制失效，用户把 n_ctx 拉到 128k 时没有任何一层能拦住，直接 OOM。所以后端不是可选项。

1.3 推理服务接入方式选型

四种候选，共同点都是提供 OpenAI 兼容的 /v1/chat/completions。这意味着上层代码只依赖 base_url 和模型名，换后端是改配置而非改代码——这是本方案最重要的解耦点。

接入代码的形状长这样，注意它完全不关心对面是 LM Studio、llama-server 还是任何别的 OpenAI 兼容服务：

# server/llm.py —— 唯一与推理后端耦合的文件
BASE = os.getenv("LLM_BASE", "http://127.0.0.1:1234/v1")
MODEL = os.getenv("LLM_MODEL", "qwen3-8b")

async def stream_chat(messages, params):
    payload = {"model": MODEL, "messages": messages,
               "stream": True, "stream_options": {"include_usage": True}, **params}
    async with httpx.AsyncClient(timeout=None) as c:
        async with c.stream("POST", f"{BASE}/chat/completions", json=payload) as r:
            async for line in r.aiter_lines():
                if line.startswith("data: ") and line[6:] != "[DONE]":
                    yield json.loads(line[6:])

1.4 接口约定（前后端契约）

不用直接透传 OpenAI 的流式结构，而是自定义五种 SSE 事件。理由：前端不必解析 choices[0].delta.content 这种三层嵌套，而且可以在流中间夹带 usage、显存水位这类只有后端知道的指标。

端点方法作用
/api/healthGET返回推理服务连通性、显存已用/总量、当前模型、后端版本
/api/modelsGET可用模型列表（id、量化、大小、是否已加载、支持的最大 ctx）
/api/models/loadPOST指定模型与 n_ctx 加载；返回实际生效值（可能被钳制）
/api/chatPOST · SSE对话主入口，流式返回 meta / delta / usage / done / error
/api/chat/stopPOST中断当前生成，已生成部分照常落盘
/api/sessionsGET/POST会话列表（含摘要与 token 占用）/ 新建
/api/sessions/{id}PATCH/DELETE重命名、归档、删除（级联删消息）
/api/sessions/{id}/messagesGET拉取历史消息，用于切换会话时恢复
/api/sessions/{id}/exportGET导出 Markdown / JSON
/api/sessions/{id}/compactPOST手动触发一次自动压缩，返回压缩摘要与前后占用

关键实现细节

SSE 响应必须带这三个头，否则会出现"等了 20 秒，然后整段文字一次性蹦出来"——这是本地流式最常见的翻车点：Cache-Control: no-cache、X-Accel-Buffering: no、Connection: keep-alive。同时 httpx 侧要显式 timeout=None，否则长回答会在默认 5 秒读超时处被掐断。

2核心功能模块

四个模块，按依赖顺序排列。M1 和 M2 是能跑起来的最小集，M3 决定这个工具能不能长期用下去。

2.1 M1 模型与参数选择

能力要点实现备注
模型列表列出本机已有模型，显示量化等级与体积，标记当前已加载代理 /v1/models，附加从文件名解析出的量化信息（Q4_K_M 等）
切换模型切换时先卸载旧模型再加载新模型，避免双份权重同时占显存lms unload --all 后 lms load；切换期间 UI 显示"加载中 Ns"
采样参数temperature / top_p / top_k / repeat_penalty / max_tokens每个参数给出安全区间，越界时钳制并在界面标注"已自动调整"
上下文长度num_ctx 是唯一会直接导致 OOM 的参数，必须按显存预算设上限上限由 4.1 的公式算出，不做成自由滑块而做成"档位选择"
系统提示词可保存多套预设（如"代码助手""翻译""严谨问答"），会话级生效存 settings 表；新建会话时可选择继承哪套预设
参数预设把一组参数存为命名预设，一键切换同上，JSON 序列化即可，不必单独建表
设计取舍

不要提供 n_ctx 的自由输入框。8GB 显存下 32k 上下文会直接溢出（见 4.1 计算），而用户在看到 OOM 之前完全没有预警。做成 4k / 8k / 16k 三档，每档标注"约占用 X GB 显存"，并且后端在 /api/models/load 里再校验一次——界面是给人看的，钳制是给系统兜底的，两者都要有。

2.2 M2 对话输入与流式输出

这一模块的技术难点不在"把字显示出来"，而在长回答下不卡、中断时不留残局、渲染时不破格式。

能力要点实现备注
输入框多行自适应高度，Enter 发送 / Shift+Enter 换行 / Esc 中断textarea + 自动 scrollHeight；输入法合成期间（compositionstart）不响应 Enter，否则中文输入会误发
流式接收fetch + ReadableStream 手动解析 SSE不用 EventSource——它只支持 GET，没法带请求体
增量渲染按帧合并，而不是每个 token 触发一次重排用 requestAnimationFrame 攒 16ms 的增量一次性写入同一个文本节点。裸写 innerText += 在 2k 字后会明显掉帧
Markdown流式过程中只做轻量转义与换行，流结束后再做完整解析与高亮边流边解析 marked 会导致代码块反复重排闪烁。本地引入 vendor/marked.min.js，不走 CDN
代码块等宽字体、横向滚动、复制按钮、语言标签高亮同样延迟到流结束；复制用 navigator.clipboard
中断生成点"停止"立即停字，已生成部分保留为正式消息前端 AbortController + 后端 asyncio.CancelledError 里把已累积内容写库
指标展示每条回答下方显示：首字延迟、生成速度 t/s、token 数调试用核心指标。8B Q4 在 4060 上应稳定在 25–40 t/s，低于 15 就说明 offload 层数不对
失败态OOM、连接断开、模型未加载 → 结构化提示 + 重试按钮绝不出现白屏或只转圈。后端把异常统一成 event: error 带 code
 
// web/app.js —— 增量渲染核心，30 行
let pending = "", raf = 0;
const node = document.createTextNode("");   // 复用同一个文本节点
bubble.appendChild(node);

function flush() { raf = 0; node.data += pending; pending = ""; }

for (const ev of parseSSE(chunk)) {
  if (ev.type === "delta") {
    pending += ev.data.t;
    if (!raf) raf = requestAnimationFrame(flush);
  }
}

2.3 M3 历史会话与上下文控制

这是整个方案里最容易被做浅的部分。绝大多数自建界面都有"会话列表"，但很少有"上下文预算可视化"——而这恰恰是本地小模型最需要的能力，因为 8B 模型的上下文窗口本来就窄。

会话管理

  • 列表按 updated_at 倒序，显示标题、模型、消息数、最后更新时间
  • 标题自动取首条用户输入的前 20 字，可手动重命名
  • 支持归档（软删除）与彻底删除（级联），删除前二次确认
  • 导出 Markdown（人读）与 JSON（机读、可再导入）
  • 会话级参数覆盖：同一会话内可以锁定某套系统提示词与采样参数

上下文控制策略

策略规则适用与代价
预算分配可用提示区 = n_ctx − max_tokens − 安全余量(256)先把输出空间留出来，否则回答会被硬截断在半句话
保留优先级系统提示词全量保留 → 最近 K 轮全量保留 → 更早的消息从最旧的开始丢弃默认策略，无需额外推理，成本最低
首尾保留保留首轮问答（常含关键设定）+ 最近 K 轮，中间丢弃适合"开头给了长篇背景资料"的场景
摘要压缩被丢弃的消息先让模型总结成一段话再拼回上下文效果好但要额外一次推理，本地 8B 上会明显变慢，默认关闭
必须做到的一点

裁剪发生时，界面必须明确告诉用户"已省略 N 条历史消息"，而不是静默截断。用户看到模型答非所问时，如果能立刻发现"哦，前半段被裁了"，排查成本从半小时降到三秒。同时上下文用量做成一个常驻进度条：低于 60% 绿色，60–85% 琥珀色，超过 85% 变红并提示"建议新建会话"。

2.3.1 自动压缩上下文（Auto-compaction）

前面的裁剪策略解决的是"装不下怎么办"——它只能丢弃。自动压缩要解决的是"丢掉太浪费"：把早期对话折叠成一段结构化摘要，用 3% 的空间保住 30% 的信息。这是本地小模型场景下的刚需，因为 8B 的上下文窗口本来就窄，而一个人的调试会话往往几十轮。

最重要的设计前提

压缩是发送时视图（send-time view），不是数据改写。数据库里的原始消息一条都不删，压缩只影响这一次请求发给模型的 payload。带来三个好处：摘要质量不满意可以换策略重压；用户随时能回看原文；压缩逻辑出 bug 时最坏情况只是这次回答变差，数据不会丢。

一、触发条件

五个条件全部满足才触发，且在每次请求发出前预检——绝不在流式生成中途打断。

#条件默认值判定逻辑与理由
C1用量超过阈值75%
可配 60–90%		预计占用 > n_ctx × 0.75。留 25% 余量是给"这一轮本身可能很长"的缓冲——等 95% 再压，往往已经来不及。
C2有足够可压的轮次≥ 3 轮可压轮次 = 总轮次 − 保护轮次。少于 3 轮时压缩收益小于摘要开销，不如直接滑窗。
C3不在生成中强制压缩只在请求前预检时发生。生成中途改变上下文会让模型输出前后矛盾，是明确禁止项。
C4冷却已过距上次压缩 ≥ 1 轮防抖。压缩会把占用从 78% 打到 41%，如果不冷却，下一轮立刻又接近阈值但可压内容太少，导致反复压、反复调模型，白白增加延迟。
C5压缩确实有效能降到 45% 以下预估压缩后的占用。如果压完仍在阈值之上（说明单条消息本身超长），则不压，直接走"单条截断"路径——压了也白压，还多花一次推理。

二、压缩粒度

粒度选择规则为什么是这个粒度
以「轮次」为单位
核心决定		1 轮 = 1 条 user + 1 条 assistant，成对处理，不可拆分按单条消息切会把一问一答拆开，摘要里出现"用户问了 X，但回答被切走"，语义直接断裂。按轮次是保证摘要在语义上自洽的最小单位。
单次压缩上限最多 12 轮 / 次避免一次压掉半个会话。压缩范围过大时摘要必然失真（把 30 轮压进 400 tokens，细节全没了）。超过上限就分多次，每轮请求各压一批。
累积方式从最旧的未压缩轮次开始向后贪心累积，直到释放量足够保证压缩区间永远是连续的前缀，摘要覆盖范围可以用一个整数 covered_turns 精确描述，不必记录区间集合。
单条超长消息单条超过 30% n_ctx 时，先做抽取式截断（保留首尾各 40%），再进摘要一条 5000 字的粘贴内容会单独吃掉大半窗口，这种消息必须先压，否则压多少轮都不够。

三、保留策略（分层）

层内容处理方式说明
L0系统提示词永不压缩里面是角色设定与硬约束，被摘要掉等于换了个人格
L1已有摘要（若有）与新内容合并后重写摘要的摘要：第二次压缩时，把旧摘要 + 新一批轮次一起喂给模型，产出覆盖范围更大的新摘要。covered_turns 单调递增
L2最近 4 轮原文保留模型需要最近的对话原文才能接上"刚才说到哪"。这 4 轮绝不动，是可配参数
L3更早的轮次压成摘要唯一被替换的层
L4单条超长消息先截断再进摘要见上表"单条超长消息"

四、摘要规格

参数取值理由
生成方式非流式，独立请求摘要不需要逐字展示，流式只会增加复杂度
temperature0.2摘要是信息压缩任务，需要稳定复现，不需要创造性
长度上限min(600, 被压原文 tokens × 18%)压缩比控制在 5:1 左右。压得太狠会丢关键约束，压得不够则省不下空间
输出结构四段固定标题：
① 目标与约束 ② 已达成的结论 ③ 关键事实与数据 ④ 未决问题		固定结构让摘要可被模型可靠消费，也让人能快速扫读。自由散文式摘要的可用性差很多
注入方式以 role: system 插入，带前缀标记形如 [对话历史摘要 · 覆盖前 N 轮 · 生成于 …]。让模型明确知道这是二手信息，不是原始对话

五、失败降级链

压缩会额外发起一次推理调用，就一定会失败（模型忙、显存紧、超时）。压缩失败绝不能让用户聊不下去，所以设计三级降级，每一级都比上一级更"笨"但更可靠：

① LLM 摘要（首选）       → 超时 20s 或返回异常
        ↓ 失败
② 抽取式压缩（本地，零推理） → 每轮取「用户问题首句 + 助手回答首 2 句」拼接
        ↓ 仍然超限
③ 滑窗丢弃（最旧轮次直接丢） → 记录丢弃数量，界面提示
        ↓ 仍然超限
   结构化报错 CTX_OVERFLOW  → 提示用户新建会话，绝不静默截断

每一档的实际使用情况通过 event: compact 里带的 mode 字段回传到界面，用户能一眼看到"这次用的是本地抽取式，不是模型摘要"。

六、可观测与人工介入

  • 消息流中插入一条灰条：「已压缩 6 轮历史 → 摘要 412 tokens（占用 78% → 41%）」，点击展开摘要全文
  • 手动入口：界面「立即压缩」按钮 + POST /api/sessions/{id}/compact，用于在长对话前主动腾空间
  • 总开关：设置里可关闭自动压缩，关闭后退回纯滑窗策略（保留策略仍然生效）
  • 缓存失效：摘要覆盖范围内的消息被编辑或删除时，标记 dirty，下次请求重算摘要
  • 统计写入会话表：compact_count、last_compact_at、累计节省 token 数
一个容易踩的坑

压缩后的 payload 里，摘要消息必须排在系统提示词之后、保留轮次之前，且要保证角色序列合法（system → user → assistant → …）。如果把摘要塞在 user 消息后面，部分推理服务会拒绝请求或让模型误判说话人。另外摘要文本里不要出现"user:" "assistant:" 这类字样，否则模型可能把它当成真的对话轮次继续模仿。

显存占用估算公式

显存占用 ≈ 权重 + KV cache + 计算缓冲

权重        ≈ 参数量 × 每参数字节数
              Q4_K_M ≈ 0.55 字节/参数   → 8B ≈ 4.7GB
              Q5_K_M ≈ 0.70 字节/参数   → 8B ≈ 5.9GB
              FP16   ≈ 2.00 字节/参数   → 8B ≈ 16GB（本机不可行）

KV cache    ≈ 2 × 层数 × KV头数 × head_dim × ctx × 字节宽
              以 Qwen3-8B（36 层 / 8 个 KV 头 / head_dim 128 / FP16）为例：
              2 × 36 × 8 × 128 × 2 = 147,456 B ≈ 144 KiB / token
              8k ≈ 1.18 GB    16k ≈ 2.36 GB    32k ≈ 4.72 GB
              KV 量化到 q8_0（1 字节/元素）后减半：32k ≈ 2.36 GB

计算缓冲    ≈ 0.5 – 0.9 GB（随 batch 与 ctx 增长）

#风险等级触发信号缓解措施备选方案
1显存溢出 OOM高加载即失败，或对话中途推理服务退出n_ctx 做成档位 + 后端二次校验；启动前查显存余量；捕获异常转成"建议降到 4k 或换 4B 模型"降低量化（Q4→Q3）、减少 GPU 卸载层数、换更小的模型
2流式被缓冲高首字延迟等于总生成时长，文字整段蹦出三个 SSE 响应头写死；httpx 用 aiter_lines 逐行 yield；前端不加任何中间层改用 WebSocket（复杂度上升，一般不需要）
3长对话前端卡顿中回答超过 1500 字后滚动掉帧、输入延迟rAF 合并增量；复用单个文本节点；Markdown 与代码高亮延迟到流结束超长消息折叠为"展开查看"；虚拟列表
4上下文静默截断中模型"忘记"前文，答非所问服务端预算计算 + 界面显式提示"已省略 N 条" + 用量进度条开启摘要压缩（额外一次推理，慢）
5依赖装不上（离线/版本无 wheel）中pip install 报编译错误或找不到包锁 Python 3.11/3.12；vendor/wheels 预置；不引入需要编译的包改用 uv 与锁文件；极端情况用便携版 Python 打包
6端口被局域网访问 / 数据外泄高同网段其它设备能打开界面只绑 127.0.0.1（不是 0.0.0.0）；前端零外链；无遥测与版本检查加本地 token 校验；防火墙入站规则限制
7杀软误报 / 打包失败低双击 exe 被拦、PyInstaller 产物缺失 dll优先用 .bat + 便携 Python，不做单文件打包改用 Tauri 壳（5.3 方案 B）
8模型许可限制低商用分发时许可不允许记录模型来源与许可证到 models.yaml；优先选 Apache-2.0 许可的模型替换为许可更宽松的同档模型

10Windows 中文路径 / 编码低启动脚本乱码、bat 执行失败脚本全 UTF-8 无 BOM；路径一律加引号；避免中文目录名改用 PowerShell 脚本（对 UTF-8 支持更好）
